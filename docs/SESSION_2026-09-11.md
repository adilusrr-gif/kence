vLLM, what else needs stabilizing, and why can another session see my

**vLLM: no, not now.** It solves concurrent-throughput pressure we don't have
evidence of, and would add an operations layer on top of infrastructure that
was actively broken (see below). Revisit only if metrics show Ollama is the
bottleneck.

session — `_get_owned_job` (`translation_routes.py`) checks `job.username`,
and `GET /api/translations` filters on it. Two tabs on one account see one
list. No change made. A genuinely adjacent hole did exist, though, and was
fixed (item 4 below).

## P0-02 production deploy — done

The live `kenceai` database was unversioned (23 tables, no `alembic_version`),
so this needed the legacy-adoption path, not a plain `alembic upgrade head`.

Sequence run: backup (`ops/backup/backup.sh`) → restore into the disposable
stack and verify (`restore.sh` + `verify_restore.sh`, **PASS**, all Postgres
row counts and Neo4j node/relationship counts matched) → regenerate manifest →
build image → `docker-compose stop backend` → `adopt_legacy_schema.py` →
migrate profile → `up -d backend`.

Result: `UNVERSIONED -> bc59de168869`. Row counts after migration identical to
the pre-migration backup, which is retained per the DR runbook.

**Actual downtime was ~23 minutes**, not the seconds expected. Two things ate
the window, both avoidable next time:

- `--expect-host` was guessed wrong. Postgres is reached through Docker's NAT,
  so `inet_server_addr()` returns the container's bridge address, not the
  loopback address the host connected to. **Read the actual value with
  `docker inspect` before opening the window, don't infer it from the
  connection string.**
- `restore.sh` failed the first time because a stale restore-test stack from a
  previous run still held its volumes, so the freshly generated Neo4j password
  never took effect ("this change will only take effect if performed before
  the database is started for the first time"). Run `restore.sh --teardown`
  first, then restore. The script does not do this itself.

## The fail-open startup gate (found, then fixed)

While redeploying, the backend logged `DB init failed — running without
persistent DB: UndefinedTable: relation "alembic_version" does not exist` —
on every boot, since 2026-09-09. `_init_db`'s broad `except Exception`
(there so the app can degrade when Postgres is unreachable) was also
swallowing schema-verification failures. The gate documented in the Stage E.3
doc as "refuses to start against an unexpected schema" was, in practice,
logging a warning and serving traffic.

Fixed in commit 6: schema verdicts now raise `SchemaVerificationError`, which
`_init_db` re-raises past the degrade handler. A missing `alembic_version`
table is translated from `ProgrammingError` into that type; `OperationalError`
(database unreachable) deliberately stays on the degrade path so losing
Postgres doesn't crash-loop the app. `tests/test_schema_gate.py` pins both.

## Repository history divergence — resolved

`p0-02-stage-e3` (and so `prerelease`) had **no common ancestor with
`master`**. The repo's history had been rewritten at some point to scrub a
committed secret; `master` moved to the cleaned lineage and this branch never
did. Different root commits, identical commit messages, different hashes
throughout.

Resolved by finding the real content-equivalence point — `65a31d5`
(prerelease) and local `master` `6411a4c` produce byte-identical trees — then
`git rebase --onto master 65a31d5 prerelease`. Diff against the pre-rebase
branch is empty: content unchanged, history linearized. `origin/master` was
fast-forwarded one commit first so the PR diff was exactly the new work.
